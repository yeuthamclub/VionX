0.1 Operating rules

1.  Do not redesign the product or substitute a different architecture
    without creating an ADR explaining the reason, impact, migration
    cost, and rollback plan.
2.  Build incrementally. Do not attempt all modules in one pass.
3.  The first objective is a runnable vertical slice: Parent Phone
    OTP/Google Sign-In -> create Household -> grant required consent ->
    create Child ID/PIN -> child login -> Today plan -> complete
    learning/task -> XP -> Coin -> Parent dashboard.
4.  Prefer a modular monolith for the backend. Do not prematurely create
    microservices.
5.  Use REST + OpenAPI for normal application APIs. Use WebSocket only
    for real-time Arena functionality.
6.  Use PostgreSQL + pgvector as the primary database. Redis is used for
    caching, queues, rate limits and ephemeral realtime state. Local
    development uses local filesystem or MinIO; production may switch to
    cloud object storage through StorageProvider. Infrastructure
    dependencies must have local implementations whenever practical.
7.  All content created by AI that can affect curriculum, answers,
    scoring, or assessment must carry provenance and a review status. AI
    must not silently become the curriculum source of truth.
8.  Child data is private by default. Do not expose precise child
    location, email, phone, school information, or unrestricted public
    chat.
9.  Parent identity supports Phone OTP + Google Sign-In. Google Sign-In
    may use Firebase Auth. Phone OTP MUST go through an internal
    OtpProvider adapter: MockOtpProvider locally and a
    Vietnam-compatible SMS/OTP provider in production. Do not hard-code
    Firebase Phone Auth as the only phone provider. Child identity uses
    Child ID + PIN and does not require phone/email.
10. Consent is versioned, auditable, scoped and revocable. Do not model
    sensitive consent as one boolean.
11. Health/activity data is read through approved health connectors
    (Android Health Connect first). Do not continuously track child GPS.
    Do not ingest workout routes for child profiles in v1.
12. Raw front-camera eye-tracking video must remain on-device by
    default; only derived reading-attention metrics may be uploaded.
13. Microphone must never run continuously in the background.
14. Eye tracking is an attention/reading-behavior signal, not proof that
    a child understood a book. Reading comprehension must be measured
    separately.
15. Talent/strength analysis is advisory. Never present it as a
    psychological diagnosis, fixed aptitude, or deterministic career
    decision.
16. Reward rules must be implemented in a configurable rule engine, not
    scattered hard-coded constants.
17. Every feature must include permissions, auditability, tests, error
    states, and migration-safe persistence.
18. When a requirement is ambiguous, use the defaults in this document
    rather than asking the product owner unless implementation is
    genuinely blocked.
19. At the end of every milestone: run lint, unit tests, integration
    tests, migration tests, API contract checks and a basic end-to-end
    flow.
20. Keep the repository runnable locally with documented commands and
    seeded demo users.

1. PRODUCT DEFINITION

1.1 Brand identity

-   Product name: VionX
-   Tagline: Think. Explore. Grow.
-   Positioning: Personalized Student & Family Development OS for Grade
    1-12.
-   Child-facing language: VionX should feel aspirational and
    age-neutral, not childish.
-   Naming rule: New modules should use the VionX brand consistently; do
    not reintroduce the former working name “CDOS” as a public-facing
    name.

1.2 Product definition

VionX is an AI-powered Student & Family Operating System for children
from Grade 1 to Grade 12. It combines personalized learning, school
score tracking, daily planning, reading, English 4 skills, sports,
talent development, cognitive games, family tasks, rewards and
educational opportunity discovery.

The system should answer two recurring questions:

-   Student: “What should I do next?”
-   Parent: “How is my child developing, and where should I invest more
    time/resources?”

The platform must not collapse a child into one overall score. Academic
mastery, school grades, English, reading, cognitive games, creative
activities, sport and habits remain separate dimensions that can be
viewed together.

2. USER ROLES AND PERMISSIONS

2.1 Parent

The Parent account is the root household identity. A parent can:

-   create and manage child profiles
-   generate/reset each child’s login ID and PIN
-   assign tasks, routines and rewards
-   enter/edit school grades
-   import books into the family library when permitted
-   manage schedules and exam dates
-   configure reward rules within system constraints
-   view reports, strength analysis and recommendations
-   approve friend/multiplayer relationships where required
-   manage privacy, consent, connected health services and
    competition-area preferences
-   disable a child login

2.2 Child

A child does not require an email address. Child login is created inside
a parent’s household.

Child can:

-   sign in using Child ID + PIN or paired device session
-   view Today plan
-   complete learning, reading, English, sport and household tasks
-   use Arena games according to limits
-   view personal progress, badges, XP, Coin balance and approved
    rewards
-   request parent approval for selected actions

Child cannot:

-   edit school grades
-   change conversion/cash-equivalent reward rules
-   modify privacy policies
-   grant/revoke parent-level consent or expose precise location
-   access parent-only analytics or other siblings’ private reports
    unless parent explicitly enables a family view

2.3 Admin / Content Editor

Admin manages:

-   curriculum versions
-   textbook/workbook imports
-   knowledge graph
-   question bank
-   AI-generated content review
-   books and content moderation
-   competition/event catalog
-   safety/moderation queues
-   product analytics and system configuration

Support fine-grained permissions such as admin, curriculum_editor,
content_reviewer, competition_editor, support_agent.

3. ARCHITECTURE DECISIONS

3.1 Frontend

Child App

-   Flutter
-   Android-first
-   tablet responsive
-   offline-capable learning packs
-   camera/microphone access only after parent consent, contextual
    disclosure and OS permission

Parent App

-   Next.js + TypeScript as responsive web/PWA for v1
-   architecture must allow later React Native or Flutter mobile shell

Admin CMS

-   Next.js + TypeScript
-   role-based navigation and data grids

3.2 Backend

-   NestJS + TypeScript
-   modular monolith
-   REST + OpenAPI
-   background jobs using Redis-backed queue
-   WebSocket gateway only for realtime Arena functionality

3.3 Data

-   PostgreSQL: primary transactional database
-   pgvector: embeddings and semantic retrieval
-   Redis: cache, distributed locks, job queue, sessions/rate
    limits/realtime ephemeral state
-   S3-compatible object storage: PDFs, EPUB, images, audio,
    submissions, generated content
-   PostgreSQL full-text search initially; add a dedicated search engine
    only after measured need

3.4 AI Provider Strategy

All model calls must go through an internal AI Gateway with provider
adapters. Do not bind application domain code directly to one vendor.

Local-first default: local inference on the Mac mini is the primary
development/test path. The default local provider is Ollama or an
OpenAI-compatible MLX server running natively on macOS. Cloud AI
providers are optional deployment adapters, not architectural
dependencies.

Interfaces required:

-   chat/reasoning model
-   small/low-cost text model
-   embedding model
-   speech-to-text
-   text-to-speech
-   image/document understanding
-   moderation/safety classifier where needed

Store model name, prompt version, token/cost metadata and provenance for
auditable AI operations.

3.5 Local-first deployment invariant

VionX must be able to run an internal alpha primarily on a Mac mini M4
with 16GB unified memory. The Mac mini is the local application server,
database server, content-processing workstation and local AI inference
host for development/internal testing.

Rules:

-   Native macOS processes are preferred for Apple-Silicon-accelerated
    AI workloads.
-   Do not run the primary local LLM inside Docker on this 16GB machine.
    Run Ollama/MLX natively so it can use Apple Silicon/Metal
    efficiently.
-   Docker is used for ARM64-compatible infrastructure services such as
    PostgreSQL/pgvector, Redis, MinIO, Mailpit and optional monitoring.
-   Every Docker image must support linux/arm64; do not silently depend
    on x86 emulation.
-   Limit Docker Desktop memory to about 5-6GB initially, leaving
    unified memory for macOS, Flutter tooling and local model inference.
    Adjust only after measuring actual pressure.
-   Keep only one medium generative model resident at a time. Use small
    quantized models for routing/classification and a 7B/8B-class
    quantized model only when necessary. Avoid >8B models as a default
    on 16GB.
-   Prefer 4K-8K inference context windows for local operation; RAG
    should retrieve a small number of high-quality chunks rather than
    sending whole chapters.
-   Content generation is queue-based and may be processed
    serially/off-hours. Interactive student requests have higher
    priority than offline generation jobs.
-   Local storage must be configurable to an external SSD/NVMe. If the
    Mac mini has only 256GB internal storage, use an external 1TB+ SSD
    for books, OCR artifacts, model files, MinIO data and backups.
-   The application must remain cloud-migratable by swapping provider
    adapters and environment configuration, not rewriting domain logic.

Recommended local resource budget

    macOS + system reserve        ~4-5 GB
    Docker infrastructure         ~4-6 GB
    Local LLM / embeddings        remaining dynamic memory
    Flutter / browser / IDE       shared with system reserve

Do not start OCR, speech transcription, a medium LLM and multiple
content-generation workers simultaneously. The job scheduler must
enforce concurrency limits appropriate to 16GB unified memory.

6. CORE DOMAIN MODULES

6.1 Authentication, Household & Consent

Parent authentication

V1 parent authentication is passwordless-first:

-   Firebase Phone Authentication using SMS OTP
-   Google Sign-In
-   link multiple Firebase auth providers to one VionX parent identity
    where possible
-   verify Firebase ID token on backend and issue/maintain VionX
    application session according to the selected session strategy
-   rate-limit abuse-sensitive auth endpoints
-   do not make email/password the default parent login flow

Child authentication

-   child profile belongs to one household
-   system generates unique Child ID/username
-   parent creates or resets 4-8 digit PIN
-   PIN stored only as an Argon2id (or approved equivalent) secure hash
-   rate-limit PIN attempts
-   optional trusted-device pairing token
-   parent can revoke all child sessions
-   child has no requirement for phone number, email or Google account

Household relationships

Support multiple parents/guardians with explicit invitation and
permission levels later. V1 can start with one owner parent plus
optional second guardian.

Consent architecture

Do not store sensitive permissions as a single parent_consent=true
field. Persist versioned consent records with at least:

    consent_records
    - id
    - household_id
    - student_id nullable
    - consent_type
    - policy_version
    - status
    - granted_by_parent_id
    - child_assent_required
    - child_assent_status
    - granted_at
    - revoked_at
    - device_id_hash / audit metadata

Initial consent scopes:

-   CORE_SERVICE
-   EDUCATION_ANALYTICS
-   AI_PERSONALIZATION
-   CAMERA_READING
-   MICROPHONE_SPEAKING
-   HEALTH_CONNECT_ACTIVITY
-   HEALTH_CONNECT_HEART_RATE (optional/separate)
-   COMPETITION_AREA

Consent must be auditable and revocable from Parent Privacy Center.

10. MASTERY ENGINE

10.1 Skill state

For each (student, skill) maintain:

-   mastery_score 0-100
-   confidence_score 0-1
-   attempt_count
-   correct_count
-   recent_accuracy
-   avg_response_time
-   current_difficulty
-   last_attempt_at
-   last_mastered_at
-   next_review_at
-   forgetting_risk

10.2 Display states

-   Not Learned
-   Introduced
-   Learning
-   Proficient
-   Mastered
-   Retained

Do not directly equate XP with mastery.

10.3 Initial algorithm

V1 may use a transparent weighted model rather than opaque ML:

    mastery_delta =
      correctness_weight
      * difficulty_weight
      * independence_weight
      * recency_weight

Hints reduce independence weight. Repeated short-interval answers have
diminishing impact. Retention review after a delay is required for
Retained.

The implementation must isolate this formula behind a strategy interface
so Bayesian/IRT models can replace it later.

14. REWARD ECONOMY

14.1 Currency model

Required default conversion:

    100 XP = 1 Coin
    1 Coin = nominal reward value 1,000 VND

Coin is a parent-managed reward unit, not a bank balance. Do not
implement cash withdrawal/payment rails in v1.

Separate:

-   lifetime_xp: progression/levels; can continue increasing
-   rewardable_xp: XP eligible for Coin conversion
-   coin_balance: redeemable family reward units
-   nominal_vnd_value: display calculation only

14.2 Daily conversion caps

Monday-Friday

Maximum converted reward per child per local day:

    20 Coins = 20,000 VND nominal value

Saturday-Sunday

Enhanced milestone mode, absolute maximum:

    50 Coins = 50,000 VND nominal value

Default weekend milestone tiers:

-   Tier 0: up to 20 Coins - normal eligible tasks
-   Tier 1: up to 30 Coins - all required daily learning tasks completed
-   Tier 2: up to 40 Coins - Tier 1 + reading goal + physical activity
    goal
-   Tier 3: up to 50 Coins - Tier 2 + one approved bonus challenge /
    family mission / advanced learning milestone

These thresholds must be stored as configurable reward rules. Parent may
make rules stricter or reduce limits, but cannot raise system safety
caps unless an administrator-level product setting later permits it.

14.3 Anti-gaming rules

-   one activity cannot award the same reward twice
-   enforce idempotency key on reward transactions
-   cap repetitive micro-actions
-   arena participation alone cannot generate unlimited XP
-   parent approval can be required for household tasks
-   excess XP beyond the daily Coin conversion limit may count toward
    level progression but does not automatically roll into
    cash-equivalent conversion the next day

All reward ledger entries are immutable. Corrections are reversal
transactions.

16. SMART READING LIBRARY

16.1 Reading workflow

    Choose Book
    -> Start Reading Session
    -> Reader presents page/chapter
    -> optional attention tracking
    -> periodic low-friction reading checks
    -> finish session
    -> comprehension check
    -> reading analytics
    -> XP eligibility

16.2 Eye/attention tracking

This is a privacy-sensitive optional feature.

Principles:

1.  Explicit parent permission and child-facing camera indicator.
2.  Prefer on-device face/eye landmark processing where practical.
3.  Do not retain raw front-camera video by default.
4.  Store derived events/metrics such as face_present,
    gaze_on_screen_probability, session_focus_ratio, with timestamps and
    confidence.
5.  Hardware/device incompatibility must not block reading.
6.  Eye tracking must not claim comprehension.
7.  Reading quality combines behavior with comprehension results.

Possible v1 reading-quality formula:

    Reading Quality =
      0.30 * session_completion
    + 0.20 * attention_signal
    + 0.50 * comprehension_score

The formula must be configurable and clearly labeled as an internal
indicator.

16.3 Daily reading mission

Parent/system can set:

-   duration target
-   chapter/page target
-   required comprehension check
-   optional genre/level

17. SPORTS, ACTIVITY & HEALTH CONNECTORS

VionX does not require continuous GPS tracking for the child. The
primary source of activity data is a connector abstraction, with Android
Health Connect as the first implementation.

17.1 Health connector architecture

    Wearable / Health App
            ↓
    Android Health Connect
            ↓
    HealthConnector adapter
            ↓
    On-device normalization
            ↓
    VionX Health Gateway
            ↓
    Daily/weekly activity summaries

Required provider interface:

    HealthConnector
    - connect()
    - disconnect()
    - getPermissions()
    - readActivities(range)
    - readSteps(range)
    - readDistance(range)
    - readCalories(range)

V1 reads only the minimum useful activity scopes:

-   exercise sessions
-   steps
-   distance
-   active/total calories where available
-   optional heart rate only behind a separate parent consent

Do not read or persist in V1:

-   workout GPS routes / ExerciseRoute for child profiles
-   medical records
-   diagnoses
-   medication
-   glucose
-   other clinical records unrelated to the product use case

Prefer storing normalized summaries rather than copying all raw samples
to the cloud.

17.2 Activity planning

System may generate non-medical, age-appropriate activity suggestions
based on:

-   age group
-   selected interests
-   time available
-   prior activity summaries
-   available equipment/space
-   parent constraints

Types include active play, walking/running, cycling, ball sports,
mobility, age-appropriate bodyweight activity and coordination/balance.

Do not diagnose health conditions or prescribe rehabilitation.
Injury/medical scenarios should direct parents to qualified
professionals.

Store planning and summary fields such as:

-   activity type
-   planned duration
-   actual duration
-   intensity category when reliably available
-   completion
-   source connector
-   personal-best metrics when relevant

19. STRENGTH / TALENT ANALYTICS

The purpose is to give parents evidence-based signals, not labels.

Inputs may include:

-   mastery growth rate
-   school grade trends
-   retention
-   voluntary engagement
-   difficulty level reached
-   problem-solving/game performance
-   coding progression
-   creative portfolio activity
-   English skill progression
-   consistency

Do not use XP or paid reward value as a strength signal.

For each domain output:

-   strength indicator 0-100
-   confidence 0-1
-   data sufficiency level
-   contributing evidence
-   trend
-   recommended next opportunities

Example:

    Logic / Problem Solving
    Indicator: 88
    Confidence: 0.82
    Evidence: strong math mastery growth, high Sudoku difficulty, chess puzzle progress
    Recommendation: consider advanced math/problem-solving club or beginner competitive programming

Never state that a child “must” pursue a career because of this profile.

    Docker Desktop RAM: 5-6 GB
    Swap: 1-2 GB

    API                 : 512 MB-1 GB
    Worker              : 512 MB-1 GB
    Redis               : 256-512 MB
    MinIO               : 256-512 MB
    Mailpit             : 128 MB
    Monitoring          : optional; disabled when memory pressure is high

31. BOOK -> KNOWLEDGE -> LEARNING DATA PIPELINE

Books are source material; they are not the core data model. VionX
converts source books into normalized document data, curriculum
mappings, skills, grounded chunks and approved learning content.

31.1 Supported source classes

    SGK  = concept/explanation/examples
    SBT  = exercise patterns/practice variations
    SGV  = learning objectives/teaching intent/common misconceptions
    Reference book = supplementary evidence; lower default trust
    Family-imported reading book = reading library; not automatically curriculum truth

Supported import formats initially:

    PDF
    EPUB
    DOCX (optional import adapter)
    Images / scanned PDF
    Google Drive selected file/folder
    Local folder

31.2 Canonical document representation

Every source converts into a common representation preserving
provenance:

    {
      "documentId": "...",
      "bookVersionId": "...",
      "grade": 6,
      "subject": "MATH",
      "bookType": "SGK",
      "curriculumVersion": "2026-2027",
      "pages": [
        {
          "page": 67,
          "blocks": [
            {"type":"heading","text":"..."},
            {"type":"paragraph","text":"..."},
            {"type":"example","text":"..."},
            {"type":"exercise","text":"..."}
          ]
        }
      ]
    }

Never discard page references during transformation.

31.3 Extraction pipeline

    SOURCE FILE
       |
       v
    File validation + hash
       |
       v
    Text-layer inspection
       |
       +--> text PDF ------> PyMuPDF fast extraction
       |
       +--> scan/image ----> local OCR
       |
       v
    Layout / structure normalization
       |
       v
    Canonical Document JSON
       |
       v
    TOC / chapter / lesson extraction
       |
       v
    Curriculum mapping proposal
       |
       v
    Concept + Skill extraction
       |
       +--> semantic chunks --> embeddings --> pgvector
       |
       +--> source mapping --> Knowledge Graph
       |
       v
    Human/admin review

Use OCR only on pages that need it. Do not OCR every page by default.

31.4 Knowledge hierarchy

    Curriculum Version
     -> Grade
     -> Subject
     -> Domain
     -> Topic
     -> Lesson
     -> Learning Objective
     -> Concept
     -> Skill

Each skill is the smallest mastery unit.

Knowledge edges:

    PREREQUISITE_OF
    PART_OF
    RELATED_TO
    NEXT_RECOMMENDED
    EQUIVALENT_OR_OVERLAP

31.5 RAG chunking

Do not chunk books by fixed token windows alone. Prefer semantic chunks
tied to:

-   heading/lesson
-   definition
-   explanation
-   worked example
-   exercise group
-   table/figure explanation

Every chunk stores:

    bookVersionId
    pageStart/pageEnd
    grade
    subject
    lessonId
    skillIds[]
    contentType
    text
    embedding
    extractionConfidence
    reviewStatus

Retrieval first filters grade/subject/skill/content type, then performs
semantic vector search.

31.6 AI Tutor grounding

Tutor pipeline:

    student question
     -> classify intent
     -> resolve student/current skill
     -> retrieve approved source chunks
     -> optionally retrieve prerequisites
     -> compose bounded prompt
     -> local/cloud model
     -> source/provenance check
     -> response

The Tutor must not answer curriculum questions from model memory when
approved evidence is available but contradictory. If evidence is
insufficient, say so and request/admin-queue missing content rather than
invent curriculum facts.

51. MAC MINI MULTI-AGENT RESOURCE MODES

The 16GB Mac mini uses time-sharing rather than maximal concurrency.

Build Mode: Docker core on, Ollama heavy model off, 1-2 Antigravity
agents maximum, Claude on demand.
AI Test Mode: Docker core on, native Ollama/MLX on, Antigravity heavy
parallel work off, batch concurrency 1 by default.
Device Test Mode: prefer one physical Android device or one emulator;
turn off unnecessary LLM/agents.

Memory pressure and swap are operational limits. Agent parallelism must
be reduced before compromising database stability or causing unreliable
AI/test behavior.
